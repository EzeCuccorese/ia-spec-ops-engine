# Spec — Deterministic SDD & Verification Engine for AI Coding Agents

**Spec** is a deterministic governance and Spec-Driven Development (**SDD**) harness at repository scope for autonomous AI coding agents and software engineers.

---

## 🎯 Purpose & Overview

Delegating complex engineering tasks to AI coding agents often breaks down due to underspecified requirements, test false-positives, and uncontrolled file mutations across unrelated codebases.

`spec` enforces a strict lifecycle:
```
init ──► agent install ──► preflight (or new) ──► plan ──► tasks ──► work ──► verify ──► finish
```

### Safety & Quality Invariants
1. **Strict Path Boundaries**: All writes and subprocess execution directories are confined strictly below the explicit project root after resolving symlinks.
2. **Cryptographic Ownership Tracking**: Files Spec generates (`.spec/policy.json`, `.spec/verification.json`, `.spec/governance.md`, the bundled skills) are recorded with SHA-256 digests in `.spec/ownership.json`; in `AGENTS.md` Spec only manages its marker-delimited block. Spec never overwrites unowned user files.
3. **Deterministic `argv` Verification**: Verification checks are declared as explicit JSON argument arrays (e.g. `["pytest", "-q"]`). They never pass through a shell interpreter (`sh`/`bash`), preventing variable leaks or injection attacks.
4. **Zero Tolerance for False Positives**: `SKIPPED`, `INCOMPLETE`, or `ERROR` statuses (including timeouts and missing CLI binaries) **never** count as `PASS`.
5. **Atomic Seal (`finish`)**: The `finish` command succeeds strictly when the latest recorded verification report in `.spec/evidence/` is an authentic `PASS`.

## 💻 Installation & Setup

### 1. Installation
From the monorepo root:

```bash
# As a global tool (recommended)
uv tool install ./packages/spec

# Or editable, into an existing environment
uv pip install -e packages/spec
```

### 2. Global Executable CLI Commands
Installation registers the global binary:
- `spec`: Master governance and SDD CLI.

Verify runtime health at any time (`spec --version` prints the version):
```bash
spec doctor          # --json for machine-readable output
```

Every subcommand accepts `--root <path>` (default: the current directory).

## 🏛️ Internal Architecture

Spec is designed in 5 strictly unidirectional layers:

```
packages/spec/
├── src/spec/
│   ├── core/                  # Path boundaries, atomic writes, SHA-256 ownership,
│   │                          # TUI, and PreflightManager (Git worktree isolation)
│   ├── governance/            # Repository policy (project.py), formal audit (audit.py)
│   ├── spec/                  # SDD state machine (workflow.py), @s scenario
│   │                          # traceability (trace.py), and TDD assist (assist.py)
│   ├── verify/                # Deterministic verification engine (engine.py)
│   ├── agents.py              # AGENTS.md governance adapter and skill installer
│   ├── cli.py                 # Master CLI dispatcher
│   └── skills/                # Packaged agent skills (spec-new, spec-plan, spec-verify, spec-finish)
└── tests/                     # Unit and end-to-end test suites
```

### Persisted Repository State (`.spec/`)

| Path | Purpose | Manually Editable? |
| --- | --- | :---: |
| `.spec/policy.json` | Project boundaries, governance policies, and invariants | **Yes** |
| `.spec/verification.json` | Explicit JSON `argv` commands, required checks, and timeouts | **Yes** |
| `.spec/state.json` | State machine snapshot of the active feature | **No** (CLI managed) |
| `.spec/ownership.json` | SHA-256 content digests of files Spec may update or delete | **No** |
| `.spec/governance.md` | Agent-facing workflow rules, imported from `AGENTS.md` | **No** (Generated by `spec agent install`) |
| `.spec/specs/<feature-slug>/` | Feature artifacts: `spec.md`, `plan.md`, `tasks.md`, `work.md` | **Yes** (Human / Agent) |
| `.spec/evidence/<feature-slug>/`| Immutable, append-only verification reports on disk | **No** (Sealed evidence) |
| `AGENTS.md` | `<!-- spec:governance -->` block importing `.spec/governance.md`; the rest of the file is yours | Outside the block |
| `CLAUDE.md` | Same block importing `AGENTS.md` (only for `spec agent install claude`) | Outside the block |
| `.agents/skills/spec-*/SKILL.md` | Bundled skills (`spec-new`, `spec-plan`, `spec-verify`, `spec-finish`); also copied to `.claude/skills/`, `.gemini/skills/` or `.codex/skills/` for `claude`, `antigravity` or `codex` | **No** |

## 📖 Practical Guide & The Complete SDD Lifecycle

### Step 1: Health Diagnostics & Repository Initialization
In any target project repository:
```bash
# 1. Verify Spec runtime diagnostics
spec doctor

# 2. Initialize the repository-local .spec/ governance structure (policy.json, verification.json)
spec init --root /path/to/project

# 3. Install the reversible agent adapter (AGENTS.md block + skills)
spec agent install --root /path/to/project --yes
```

`spec agent install [agent]` accepts one of `agents` (default), `antigravity`, `claude`,
`cursor`, `windsurf`, `aider`, `copilot`, `gemini`, `codex` or `custom` (`spec agent install --help`
lists them); an agent with its own skills folder (`claude`, `antigravity`, `codex`) gets it only
when named. `--file` changes the target file for `custom`, and `--yes` skips prompts.

---

### Step 2: Pre-Flight Baseline & Git Worktree Isolation (`spec preflight`)
Before introducing dirty changes or new branches, validate baseline checks and isolate work in a worktree:
```bash
spec preflight "user-auth" --from "main" --branch "feature/user-auth" --root /path/to/project
```
- Fetches the base branch (`--from`, default the current branch) and fast-forwards it when it is checked out and clean.
- Runs the checks of `.spec/verification.json` on the base branch; with no checks configured, or any failing, it reports `FAIL` and stops.
- Provisions a Git worktree for the target branch (`--branch`, default `feature/<name>`) at `../workspace-<branch>`, copying `.spec/`, `.agents/` and `.env*` and symlinking `.venv`/`node_modules`/`.gradle`; `--no-worktree` instead switches the current checkout to that branch (`git switch -c` from the base, or `git switch` when it already exists) and fails before running any check if tracked files have uncommitted changes.
- Creates the active specification (`--description` fills it) and prints the directory where the agent must work; `--json` prints the result (`"status": "READY"` or `"FAIL"`). Run the following steps from that directory.

---

### Step 3: Formal Specification (`spec new`)
`spec preflight` already created the specification. Without preflight, create it directly:
```bash
spec new "user-auth" --description "JWT authentication with token rotation"
```
Either way the result is `.spec/specs/user-auth/spec.md`; define the functionality there with explicit, observable acceptance criteria. Each acceptance scenario must be tagged with stable identifiers (`@s1`, `@s2`, etc.) in Gherkin format (`Given / When / Then`).

---

### Step 4: Technical Architecture & Task Breakdown (`spec plan` & `spec tasks`)
```bash
# 1. Generate architectural implementation plan scaffold
spec plan

# 2. Breakdown atomic development tasks
spec tasks
```
Produces `plan.md` (architectural decisions, file modifications) and `tasks.md` (ordered atomic tasks mapped to `@s` scenarios).

---

### Step 5: Test-First Assisted Implementation (`spec work` & `spec test-assist`)
```bash
# Formally enter the active coding phase
spec work

# Get guidance on the next uncovered @s scenario to implement in unit tests
spec test-assist --next

# Where the workflow stands (also --json)
spec status
```

---

### Step 6: Deterministic Verification (`spec verify`)
Declare test commands in `.spec/verification.json`:
```json
{
  "schema_version": 1,
  "checks": [
    {
      "id": "unit-tests",
      "command": ["pytest", "-q"],
      "required": true,
      "timeout_seconds": 300
    },
    {
      "id": "linter",
      "command": ["ruff", "check"],
      "required": true,
      "timeout_seconds": 60
    }
  ]
}
```
Run verification:
```bash
spec verify
# Or with JSON output for automated pipelines:
spec verify --json
```
Each run produces an immutable audit report in `.spec/evidence/<feature-slug>/`.

---

### Step 7: Repository Audit (`spec audit`)

Verifies the harness, state coherence, artifact completeness, scenario traceability, recorded evidence and workspace hygiene:
```bash
spec audit           # --json for machine-readable output
```

---

### Step 8: Completion & Sealing (`spec finish`)
```bash
spec finish
```
Verifies that the latest recorded verification status was strictly `PASS` and seals the feature as completed.

---

### Clean Adapter Uninstallation
To remove the adapter (the `AGENTS.md` block, `.spec/governance.md` and the skills) without touching unowned files:
```bash
# Dry-run preview (default)
spec agent uninstall

# Apply deletion after SHA-256 ownership digest validation
spec agent uninstall --apply
```
