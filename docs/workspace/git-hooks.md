# Gestor de Git Hooks & Quality Gate Multi-Stack (`ws hooks`)

El módulo **Git Hooks de Workspace Engine** provee un sistema automatizado y determinista de control de calidad, seguridad y cumplimiento de políticas de ingeniería que se ejecuta localmente previo a cada `git push`.

---

## 🎯 Propósito y Beneficios

- **Detección Temprana (Shift-Left)**: Atrapa errores de sintaxis, imports no definidos, fallos de tipado y tests rotos en la máquina del desarrollador en menos de 5 segundos, antes de enviarlos a GitHub Actions.
- **Prevención Absoluta de Fugas de Secretos**: Bloquea de inmediato el envío de archivos `.env`, claves privadas o API keys hardcodeadas en el diff.
- **Cumplimiento Estricto de Políticas Git**: Asegura Conventional Commits en inglés y **CERO menciones de Inteligencia Artificial ni emojis de robot 🤖** en los commits del proyecto.
- **Agnóstico y Multi-Lenguaje**: Detecta automáticamente el stack tecnológico del repositorio (Python, Node/React, Java/Kotlin, Go, Rust, Flutter, etc.) y ejecuta los linters y pruebas correspondientes sin configuración manual.

---

## 🛡️ Las 4 Etapas del Quality Gate

Al ejecutar `git push`, el hook pre-push ejecuta secuencialmente 4 compuertas de calidad:

```
[Quality Gate Pre-Push Hook] Verificando calidad y seguridad antes de enviar cambios...
🔒 [1/4] Verificando seguridad y escaneo de secretos...
✔ Seguridad y Secretos: PASS
📝 [2/4] Verificando políticas de commit y reglas Git...
✔ Políticas Git y Cero menciones IA: PASS
🔍 [3/4] Ejecutando análisis estático y linters por stack...
✔ Linters y Análisis Estático: PASS
🧪 [4/4] Ejecutando suites de tests automáticas...
✔ Suites de Tests: PASS
🚀 Todo en orden. Procediendo con git push...
```

---

### 🔒 Etapa 1: Seguridad y Escaneo de Secretos
1. **Archivos Prohibidos Trackeados**:
   - Bloquea el push si se detectan archivos como `.env`, `.env.local`, `*.pem`, `*.key`, `id_rsa`, `id_ed25519`, `credentials.json` o `.DS_Store` trackeados por Git.
   - Permite explícitamente plantillas versionadas como `.env.example` o `*.template`.
2. **Escaneo de Tokens en Diffs Salientes**:
   - Escanea el diff en busca de patrones de claves privadas (`BEGIN RSA/OPENSSH PRIVATE KEY`), API keys de OpenAI (`sk-...`), tokens de GitHub (`ghp_...`), credenciales AWS (`AKIA...`) y Google Cloud API keys (`AIza...`).

---

### 📝 Etapa 2: Políticas Git (Zero AI Mentions)
- Inspecciona los mensajes de commit recientes para asegurar que **NO contengan** frases como:
  - *"Generated by AI"* / *"Generated with AI"*
  - *"Co-authored-by: Claude/GPT/Gemini"*
  - Emojis de robots (🤖, 🦾).
- Fomenta el uso de **Conventional Commits** en inglés imperativo (`type(scope): description`).

---

### 🔍 Etapa 3: Linters y Análisis Estático Multi-Stack

El hook detecta la presencia de archivos de configuración y ejecuta el linter apropiado:

| Stack / Runtime | Herramienta Ejecutada | Condiciones de Detección |
| :--- | :--- | :--- |
| **Python** | `Ruff` (vía binario local o `uv run --with ruff ruff check .`) / `Flake8` | `pyproject.toml`, `pytest.ini`, `requirements.txt` o `backend/` |
| **Node.js / React / TypeScript** | `npm run lint` y `npm run typecheck` | `package.json` en root, `frontend/`, `client/`, `ui/` o `web/` |
| **Go** | `go vet ./...` | `go.mod` |
| **Rust** | `cargo clippy -- -D warnings` | `Cargo.toml` |
| **Flutter / Dart** | `flutter analyze` o `dart analyze` | `pubspec.yaml` |
| **Java / Kotlin** | `spotlessCheck` (Gradle) / `checkstyle:check` (Maven) | `build.gradle`, `build.gradle.kts` o `pom.xml` |

---

### 🧪 Etapa 4: Harnés de Pruebas Automáticas

Ejecuta las suites de tests unitarios e integración según el stack del repositorio:

| Lenguaje / Framework | Comando de Tests |
| :--- | :--- |
| **Python** | `pytest` (en root o `backend/tests`) |
| **Node / React / Frontend** | `npm test` (en root o subdirectorios `frontend/`, `client/`, etc.) |
| **Go** | `go test ./...` |
| **Rust** | `cargo test` |
| **Flutter / Dart** | `flutter test` o `dart test` |
| **Java / Kotlin** | `./gradlew test` (o `gradle test`) / `./mvnw test` (o `mvn test`) |
| **.NET / C#** | `dotnet test` |
| **Ruby** | `bundle exec rake test` o `bundle exec rspec` |
| **PHP** | `composer test` o `./vendor/bin/phpunit` |

## 💻 Uso desde la CLI (`ws hooks`)

### 1. Consultar el Estado de los Hooks
Muestra el diagnóstico tanto del repositorio local actual como de la configuración global de la máquina:

```bash
ws hooks status
```

**Ejemplo de Salida**:

---

### 2. Instalar el Hook en el Repositorio Local
Crea `.githooks/pre-push`, otorga permisos ejecutables y configura `git config core.hooksPath .githooks`:

```bash
ws hooks install
```

Para forzar la sobreescritura de un hook preexistente:
```bash
ws hooks install --force
```

---

### 3. Instalar el Hook Globalmente (Toda la Máquina)
Crea `~/.githooks/pre-push` y configura `git config --global core.hooksPath ~/.githooks`. Aplica de inmediato a todos los repositorios clonados o por clonar:

```bash
ws hooks install --global
```

---

### 4. Desinstalar Hooks
Para desinstalar y desvincular la configuración local:
```bash
ws hooks uninstall
```

Para desinstalar la configuración global del sistema:
```bash
ws hooks uninstall --global
```

---

## 🔗 Delegación en Hooks Específicos de Proyecto

Si un repositorio particular define su propio hook en `.githooks/pre-push` o `.git/hooks/pre-push`, el hook global **delega automáticamente la ejecución en el hook local del proyecto**, evitando conflictos y respetando pipelines personalizados.
