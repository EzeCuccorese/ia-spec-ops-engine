# Spec-Driven Development (SDD) — Reglas Centrales y Ciclo de Vida Paso a Paso

## 1. Ciclo de Vida Estricto (Puntos de Control Humano)
El desarrollo de features DEBE avanzar secuencialmente, requiriendo revisión y aprobación humana antes de iniciar cada fase:
1. `/sdd-specify`: Especificación funcional (`spec.md`).
2. `/sdd-clarify`: Resolución de ambigüedades y análisis de riesgos (`clarify.md`).
3. `/sdd-plan`: Blueprint técnico y contratos formales de datos (`plan.md`).
4. `/sdd-checklist`: Quality gates y Definition of Done (`checklist.md`).
5. `/sdd-tasks`: Desglose atomizado de tareas ejecutables (`tasks.md`).
6. `/sdd-analyze`: Auditoría estática cruzada entre artefactos.
7. `/sdd-exec`: Ejecución iterativa de tareas con Agente Worker y Agente QA.
8. `/sdd-converge`: Verificación final de convergencia y criterios de aceptación Gherkin.

*Nota*: Para correcciones rápidas de bugs, usar exclusivamente `sdd quick`.

## 2. Pilares de SDD
- **Contratos Primero**: Definir interfaces TypeScript, esquemas Zod o DTOs Java antes de implementar la lógica.
- **Harnés de Pruebas (Test-First)**: Escribir pruebas unitarias/integración (Rojo) antes de la lógica de negocio.
- **Implementación Mínima**: Escribir el código estrictamente necesario para cumplir el contrato y pasar la prueba (Verde).
- **Detección Temprana**: Ejecutar linters y verificar lecturas de confirmación tras mutaciones.

## 3. Reglas de Git y Seguridad
- **Conventional Commits**: Escribir mensajes de commit en inglés (`type(scope): description`) en minúsculas e imperativo.
- **ZERO AI MENTIONS / CERO MENCIONES DE IA**: Nunca incluir frases como "Generado con IA" ni emojis de robots 🤖 en PRs, commits o comentarios.
- **Seguridad y Privacidad**: Cero secretos hardcodeados. Cero PII guardada en logs.

## 4. Protocolo Híbrido para Habilidades de Agentes (Determinismo + Validación Dinámica de IA)
Al ejecutar cualquier habilidad (ej. `sdd-init`, `sdd-verify`, `sdd-constitution`, `sdd-plan`), el agente DEBE cumplir 3 fases:
1. **Fase 1 (Determinística)**: Ejecutar herramientas CLI / scripts estáticos (`sdd ...`).
2. **Fase 2 (Auditoría Dinámica de IA)**: Inspeccionar el código fuente del repositorio.
3. **Fase 3 (Enriquecimiento Explícito)**: Inyectar las reglas y buenas prácticas descubiertas en `.specify/constitution/constitution.md`.

# Regla Global 01: Comportamiento e Interacción del Agente de IA

## 1. Guardrails de Ejecución y Anti-Looping
- **Anti-Doom-Loops**: Si una solución técnica o comando falla 2 veces consecutivas, el agente DEBE detenerse, reconsiderar la estrategia de raíz o solicitar aclaración al usuario. Prohibido insistir en bucles de error.
- **Edición Mínima y Diff Limpio**: Modificar estrictamente las líneas necesarias para cumplir el objetivo. No alterar espacios en blanco, tabulaciones ni saltos de línea en código no relacionado para mantener limpio el historial de cambios (*diff*).
- **Confirmación Post-Mutación**: Tras cualquier mutación en recursos (código fuente, API, base de datos, variables de entorno), es obligatorio ejecutar una lectura de verificación (GET, linter, tests de validación) antes de dar por completado el paso.

## 2. Comunicación y Respuestas
- **No Repetir Código**: Prohibido duplicar bloques de código enteros en el resumen final de la respuesta si ya fueron persistidos en el sistema de archivos. Limitarse a listar los archivos afectados y explicar las decisiones tomadas.
- **Reporte Fiel de Resultados**: Si una prueba o comando falla, reportar el error exacto de forma transparente sin ocultar diagnósticos ni asumir falsos positivos.
- **Claridad y Concisión**: Respuestas estructuradas, profesionales y directas al grano, redactadas en español técnico.

# Regla Global 02: Flujo de Trabajo Git y Commits

## 1. Conventional Commits Estricto
- Los mensajes de commit DEBEN redactarse en **inglés**, usando el formato estándar: `type(scope): description`.
- Tipos permitidos: `feat`, `fix`, `refactor`, `perf`, `docs`, `test`, `chore`, `ci`.
- El mensaje debe estar en minúsculas, en modo imperativo y sin punto final (ej: `feat(auth): add jwt validation middleware`).

## 2. POLÍTICA ABSOLUTA: CERO MENCIONES DE IA
- **PROHIBIDO** incluir cualquier mención de Inteligencia Artificial en commits, mensajes de PR, descripciones de ramas o comentarios de código.
- **PROHIBIDO** incluir frases como "Generated by AI", "Co-authored by Claude/Cursor/Gemini", "AI-assisted" ni emojis de robots (🤖, 🦾, etc.).

## 3. Gestión de Ramas y Tests Obligatorios
- Los commits y pushes son libres en ramas de características (*feature branches*).
- En ramas protegidas (`main`, `master`, `develop`, `staging`), se requiere autorización explícita por escrito del usuario.
- Antes de realizar cualquier push, se debe ejecutar obligatoriamente la suite de tests correspondiente (`pytest`, `npm test`, `./gradlew test`, `./mvnw test`). Si algún test falla, queda terminantemente prohibido hacer push. Prohibido el uso de `--no-verify`.

# Regla Global 03: Seguridad y Privacidad

## 1. Cero Secretos Hardcodeados
- **PROHIBIDO** incluir contraseñas, API keys, private keys, JWT secrets o tokens en archivos versionados por git.
- Usar variables de entorno (`.env`, `.env.secrets`) o sistemas de gestión de secretos (Vault, AWS Secrets Manager, etc.).
- Las plantillas `.env.example` deben contener exclusivamente nombres de variables con valores ficticios o vacíos.

## 2. Privacidad y Cero PII en Logs
- **PROHIBIDO** registrar en logs Información de Identificación Personal (PII): nombres reales, emails, documentos de identidad, números telefónicos, direcciones.
- **PROHIBIDO** registrar datos financieros sensibles: números de tarjeta de crédito/débito, CVV, códigos CBU/CVU o contraseñas.
- En caso de requerir trazabilidad de un usuario, registrar únicamente identificadores anónimos o UUIDs de negocio ofuscados.

## 3. Prevención de Ejecución de Comandos Peligrosos
- Prohibido ejecutar comandos destructivos directos sin validación (`rm -rf /`, piping remoto `curl ... | sh`, `drop database`).

# Regla Global 04: Ciclo de Vida SDD y Puntos de Control

## 1. Ciclo de Vida Estricto de 8 Fases
Todo desarrollo de características avanza de forma secuencial, requiriendo revisión y aprobación humana antes de pasar a la siguiente fase:
1. `/sdd-specify`: Especificación funcional (`spec.md`).
2. `/sdd-clarify`: Resolución de ambigüedades y análisis de riesgos (`clarify.md`).
3. `/sdd-plan`: Blueprint técnico y contratos formales de datos (`plan.md`).
4. `/sdd-checklist`: Quality gates y Definition of Done (`checklist.md`).
5. `/sdd-tasks`: Desglose atomizado de tareas ejecutables (`tasks.md`).
6. `/sdd-analyze`: Auditoría estática cruzada entre artefactos.
7. `/sdd-exec`: Ejecución iterativa de tareas con Agente Worker y Agente QA Reviewer.
8. `/sdd-converge`: Verificación final de convergencia y criterios de aceptación Gherkin.

*Para correcciones rápidas de bugs o parches pequeños, usar exclusivamente `sdd quick`.*

## 2. Los 4 Pilares de SDD
- **Contratos Primero**: Definir interfaces TypeScript, esquemas Zod, DTOs Java o modelos Pydantic antes de implementar lógica de negocio.
- **Harnés de Pruebas (Test-First)**: Escribir la suite de pruebas unitarias/integración (Rojo) antes del código de negocio (Verde).
- **Implementación Mínima**: Escribir únicamente el código necesario para satisfacer el contrato y pasar los tests (YAGNI).
- **Detección Temprana**: Ejecutar linters estáticos y realizar lecturas de confirmación post-mutación.
